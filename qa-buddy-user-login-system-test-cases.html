1. Requirement Analysis

The feature under test is a User Login System that authenticates users via email and password credentials. Upon successful authentication, users are redirected to a dashboard. The system enforces input validation rules and provides brute-force protection via account lockout.

AttributeDetail
FeatureUser Login / Authentication
Actor(s)Registered User
System BoundaryLogin page → Authentication service → Dashboard redirect
Email ConstraintMust be in valid email format (stated)
Password ConstraintMinimum 8 characters (stated)
Lockout RuleAccount locked for 15 minutes after 5 consecutive failed attempts (stated)
Forgot PasswordOption must be available on the login page (stated)
Success BehaviorRedirect to dashboard on successful login (stated)
Max password length[ASSUMPTION] No upper limit stated — assumed unconstrained unless defined elsewhere
Account existence check[ASSUMPTION] Login requires a pre-registered account in the system
Lockout reset[ASSUMPTION] Lockout auto-releases after 15 minutes; no admin-unlock mechanism described
Case sensitivity[ASSUMPTION] Email is case-insensitive; password is case-sensitive (industry norm)

2. Testing Scope

In Scope

  • Email format validation on the login form
  • Password minimum-length enforcement
  • Successful login and dashboard redirect
  • Failed login with incorrect credentials
  • Account lockout after 5 failed attempts
  • 15-minute lockout duration and auto-unlock
  • Presence and functionality of "Forgot Password" link
  • Empty field submissions
  • Boundary values for password length
  • Edge cases: special characters, SQL injection patterns, concurrent sessions

Out of Scope

  • User registration / sign-up flow (not specified)
  • Dashboard content and functionality (not specified)
  • Password reset / recovery flow internals (not specified)
  • OAuth / SSO / third-party login (not specified)
  • Session timeout and session management (not specified)
  • Two-factor authentication (not specified)
  • Performance / load testing (not specified)

3. Preconditions

  1. The login page is accessible via a supported web browser.
  2. At least one registered user account exists in the system with known valid credentials.
  3. The test environment is configured and running with a reachable authentication service.
  4. The account used for lockout tests is reset to 0 failed attempts before each lockout test.
  5. Network connectivity between the test client and the server is stable.
  6. [ASSUMPTION] Test data includes accounts in both locked and unlocked states where required.

11. Requirement Gaps & Ambiguities

  • Maximum password length is undefined. Q: Is there an upper bound on password length? Without this, boundary testing is incomplete and very long passwords could cause DoS via bcrypt cost.
  • Error message wording is not specified. Q: Should the error message be generic ("Invalid credentials") for both wrong password and unregistered email, or different? Generic messages prevent email enumeration — this should be explicitly decided.
  • Lockout reset mechanism is not defined. Q: Does the lockout auto-expire after exactly 15 minutes from the first failed attempt, the 5th failed attempt, or the most recent attempt? Is there an admin override to unlock accounts?
  • Failed attempt counter reset policy is not specified. Q: Does a successful login reset the failed attempt counter to 0? Does the counter reset automatically after 15 minutes even without a successful login?
  • Email case sensitivity is not defined. Q: Is email matching case-insensitive (industry standard) or case-sensitive? This directly impacts TC-002.
  • "Forgot Password" flow internals are not specified. Q: What does the Forgot Password flow do? (Email link, OTP, security questions?) This is out of scope for this document but will require its own test cases.
  • No mention of HTTPS / secure transport. Q: Is the login page served over HTTPS? Are credentials transmitted securely? This is a security requirement that should be stated explicitly.
  • Multiple concurrent active sessions not addressed. Q: Can the same user be logged in from multiple devices simultaneously? If not, what is the expected behavior when a second login occurs?

12. Testing Summary

A total of 22 test cases have been generated for the User Login System, providing comprehensive coverage across authentication, input validation, brute-force protection, and recovery flows. Critical risk areas include the account lockout mechanism (TC-013, TC-014, TC-017, TC-018) and security hardening (TC-019), both of which are rated Critical severity and should be prioritized in the first test execution cycle. Eight requirement gaps were identified — notably the undefined lockout reset policy, missing maximum password length, and unspecified error message wording — which must be resolved before the test suite can be considered complete. All High-priority test cases (15 of 22) are strong candidates for automated regression testing, with UI automation recommended via Playwright and API-layer state seeding for lockout-related scenarios.
